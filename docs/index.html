What it finds

Seven rule families covering what per-module tools, Java-only analysers and manual review all miss.

Dead code
Code, configuration and content that nothing consumes any more.
AEM-DEAD-001 … 005
OSGi configurations whose PID matches no component, OCD properties nothing reads, services with zero injections, Sling Models nothing adapts, clientlib categories nothing includes.
Duplication
Two things claiming the same request or the same PID.
AEM-DUP-001 … 010
Duplicate servlet endpoints, conflicting configuration for one PID, two models bound to the same resource type, and cloned Java blocks from the embedded PMD CPD scan.
Cloud Service parity
The checks Cloud Manager runs, available before you push.
AEM-CLOUD-001 … 005
Plaintext secrets, JSPs, unmapped service users, deprecated APIs and configuration in runmode folders AEM as a Cloud Service does not read.
Quality gates
Rule ids that mirror Cloud Manager, so waivers keep their meaning.
AEM-QUAL-001 … 005
CQBP-75 path-bound servlets, CQBP-84 provider-type implementations, AMSCORE-554 scheduler use, AEM-3 component thread safety and rejected administrative logins.
Performance
Resources and queries that cost more than they should.
AEM-PERF-001 … 004
Unclosed resource resolvers and JCR sessions, Oak queries without a path or node-type restriction, and queries with no result limit.
Component compatibility
Components that stop working when authoring moves to Touch UI.
AEM-COMP-001
Classic UI dialog.xml definitions that AEM as a Cloud Service cannot edit.
Security
Escaping and redirect holes a Java analyser cannot see.
AEM-SEC-001, AEM-SEC-002
context='unsafe' in HTL (invisible to any bytecode-level rule) and request parameters flowing into redirects or outbound requests.

Three ways in

To get a first report nothing needs configuring: no flags, no project-root argument, no config file.

bash · Java 21 required, nothing else
HOST=https://github.com/RohithV16/aem-code-analyser
curl -LO "$HOST/releases/latest/download/aem-analyser-cli.jar"
java -jar aem-analyser-cli.jar ~/my-aem-project

Self-contained jar. At the reactor root it scans the whole reactor; in a module directory it walks up to the reactor that owns it; in any subdirectory it finds the nearest pom.xml above.

pom.xml · at the reactor root
<build>
  <plugins>
    <plugin>
      <groupId>io.github.rohithv16</groupId>
      <artifactId>aem-analyser-maven-plugin</artifactId>
      <version>1.0.10</version>
      <!-- once, at the reactor root: module-by-module scans cannot see cross-module findings -->
      <inherited>false</inherited>
      <executions>
        <execution>
          <phase>verify</phase>
          <goals><goal>report</goal></goals>
          <configuration>
            <formats>SARIF,HTML</formats>
            <outputFile>${project.build.directory}/aem-analyser</outputFile>
          </configuration>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

Comes from Maven Central: no <pluginRepositories>, no token. mvn verify then writes target/aem-analyser/aem-analyser.sarif and target/aem-analyser/aem-analyser-report.html.

bash · builds once, then analyses
git clone https://github.com/RohithV16/aem-code-analyser
cd aem-code-analyser
scripts/run-from-source.sh ~/my-aem-project

Leave the path out to analyse the current directory.

Gate

Make it fail the build, on purpose

pom.xml · report → check, failing on errors
<execution>
  <phase>verify</phase>
  <goals><goal>check</goal></goals>
  <configuration>
    <failOn>ERROR</failOn>
  </configuration>
</execution>
  • report never fails the build: it only writes reports.
  • check fails the build when the gate trips — any ERROR finding by default, or whatever --fail-on / the coverage and duplication thresholds say.
  • CLI exit codes: 0 clean · 1 gate failed · 2 the analysis itself could not run.

What it runs on, and what it will not tell you

Everything below is checked by the project's own test suite or visible in the report.

Targets
AEM 6.5 and AEM as a Cloud Service projects.
Maven reactors with core, ui.apps, ui.config, dispatcher
Cloud Service rules are the ones that matter on AEMaaCS; the dead-code, duplication and security rules apply to both.
Runtime
Java 21 to run it. The analysed project keeps its own target.
No AEM instance, no network, no credentials
Sources are parsed, not compiled, so a Java 8 or 11 codebase is fine. A full reactor scan takes about a second on the fixture in this repository and a few seconds on a large one.
Known limits
Static analysis guesses; the report says where it guessed.
Run Health tab · --verbose · allowlists
Files that could not be parsed appear as diagnostics rather than being dropped silently, a clean run with diagnostics is not a clean run, and every rule can be muted or baselined when a finding is a false positive.
Not covered
Nothing that needs a running instance.
No runtime profiling, no dispatcher rule simulation
Content on author or publish, live OSGi state, and performance under load are out of scope — this reads the repository the build produces.
