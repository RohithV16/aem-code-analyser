Dead code

9 issues

Code, configuration and content with no remaining consumer.

AEM-DEAD-001#OrphanedOsgiConfiguration

ERROR 15 min fix Bug

Orphaned OSGi Configuration without matching component or platform PID.

Why it matters

A configuration file whose PID matches no component, no @ObjectClassDefinition and no platform factory PID never takes effect. At best it is dead weight in the content package; at worst it is a typo that silently stops the configuration you meant to ship, and the service starts with framework defaults on AEM as a Cloud Service.

How to fix it

Either delete the file or rename it so its PID is the component's fully qualified class name (or a factory PID the component declares). Verify with the Configuration console that the service now reads your properties.

text · before
ui.config/.../config/com.acme.OldSearchService.cfg.json
# class was renamed to SearchService; nothing reads this PID
text · after
ui.config/.../config/com.acme.core.services.SearchService.cfg.json

AEM-DEAD-002A#GhostConfigurationProperty

WARNING 10 min fix Code smell

Configuration property does not exist in target @ObjectClassDefinition.

Why it matters

A property that the component's @ObjectClassDefinition does not declare is dropped during binding. The configuration looks correct in the repository, so the symptom is an unexplained default value at runtime rather than a validation error.

How to fix it

Remove the property, correct its spelling, or add an @AttributeDefinition that declares it. Configuration and OCD must describe the same set of properties.

json · before
{
  "serachPath": "/content/dam"
}
json · after
{
  "searchPath": "/content/dam"
}

AEM-DEAD-002B#UnconsumedOcdProperty

WARNING 10 min fix Code smell

OCD Attribute method is never consumed by designating Java component.

Why it matters

An OCD attribute that no code reads is a setting users can change with no effect. It usually survives a refactor that removed the code path but not the interface method.

How to fix it

Inject the configuration and read the attribute, or delete it from the @ObjectClassDefinition so the configuration console stops offering a dead switch.

java · before
@ObjectClassDefinition(name = "Search Service")
public @interface Config {

    // nothing in the bundle calls this
    int legacyTimeoutSeconds() default 30;
}
java · after
@Activate
void activate(Config config) {
    this.timeout = Duration.ofSeconds(config.timeoutSeconds());
}

AEM-DEAD-003A#UnusedOsgiService

WARNING 30 min fix Bug

OSGi Service has zero injections across bundles and is not a system entry point.

Why it matters

A registered OSGi service that nothing injects and that no framework calls is code the build still compiles, tests and deploys. On AEM as a Cloud Service it also keeps its dependencies and configuration alive.

How to fix it

Inject the service where it was meant to be used, drop the service = ... registration so the class becomes a plain component, or export its package when it is a deliberate API for other bundles.

java · before
@Component(service = LegacyImportService.class)
public class LegacyImportService {
    // no @Reference to this type anywhere in the reactor
}
java · after
@Component
public class ImportJobConsumer implements JobConsumer {
    // used through the Sling Job API, not through an injected reference
}

INFO 5 min fix Code smell

Sling Model has zero Java adaptations and no resourceType binding.

Why it matters

A Sling Model that no template adapts from and that no resourceType binds is never instantiated. It is often a model that survived the deletion of its component.

AEM-DEAD-003C#InactiveDelayedComponent

WARNING 10 min fix Code smell

Component provides no service interfaces and immediate = false.

Why it matters

With immediate = false and no service interface, an OSGi component is delayed and nothing can ever obtain it, so its @Activate never runs. Any startup work it performs — schedulers, caches, listeners — silently does not happen.

How to fix it

Set immediate = true for components that must start with the bundle, or register a service interface so the component is created on first injection. Delete it if neither is intended.

java · before
@Component(immediate = false)
public class CacheWarmer {
    @Activate
    void activate() { /* never called */ }
}
java · after
@Component(immediate = true)
public class CacheWarmer {
    @Activate
    void activate() { warm(); }
}

AEM-DEAD-004#BrokenHtlReference

ERROR 15 min fix Bug

HTL template references non-existent Java class or Sling Model.

Why it matters

An HTL expression that names a class which does not exist fails at render time, not at build time, so the page breaks in the author or publish instance rather than in CI. It is usually a package move or a rename that missed the template.

How to fix it

Point data-sly-use at the current fully qualified class name, and confirm the class lives in a bundle the template's package can see.

html · before
<sly data-sly-use.model="com.acme.core.models.OldHeroModel"/>
html · after
<sly data-sly-use.model="com.acme.core.models.HeroModel"/>

INFO 10 min fix Code smell

A client library category is never referenced by an HTL/JSP template or another client library.

Why it matters

A client library no page, component or other clientlib includes is still built and deployed. Dead clientlibs usually carry JS and CSS that also hide unused configuration and third-party dependencies.

AEM-DEAD-007#BrokenHtlInclude

WARNING 15 min fix Bug

HTL data-sly-include target is missing or forms an include cycle.

Why it matters

Sightly resolves data-sly-include while rendering, so a renamed or mis-pathed include is invisible to the build. It surfaces only as an empty region on one page, long after the template was moved. An include cycle is worse: rendering recurses until the request is aborted.

How to fix it

Correct the include path to an existing template relative to the including file, or break the cycle by factoring the shared markup into a leaf template that both sides include.

html · before
<!-- components/card/card.html -->
<sly data-sly-include="card-details.html"/>

<!-- components/card/details.html (renamed to card-details.html) -->
html · after
<sly data-sly-include="card-details.html"/>

Duplication

4 issues

Two things claiming the same request, PID, resource type or code block.

AEM-DUP-001#DuplicateServletEndpoint

ERROR 20 min fix Bug

Multiple OSGi servlets claim identical paths or resourceTypes/selectors/methods without ranking distinction.

Why it matters

Two servlets that answer the same request make the response depend on registration order and service ranking. On a publish tier the result can differ between instances, which is the hardest class of bug to reproduce.

How to fix it

Merge the servlets, or give each one a distinct contract: a different resource type, selectors, extension or HTTP method. Reach for an explicit service.ranking only when one servlet must override a product servlet, and document why.

java · before
@SlingServlet(paths = "/bin/acme/search", methods = "GET")
public class SearchServlet extends SlingAllMethodsServlet { }

@SlingServlet(paths = "/bin/acme/search", methods = "GET")
public class SearchServletV2 extends SlingAllMethodsServlet { }
java · after
@SlingServlet(resourceTypes = "acme/components/search",
              selectors = "results", extensions = "json", methods = "GET")
public class SearchResultsServlet extends SlingAllMethodsServlet { }

@SlingServlet(resourceTypes = "acme/components/search",
              selectors = "suggest", extensions = "json", methods = "GET")
public class SearchSuggestServlet extends SlingAllMethodsServlet { }

AEM-DUP-002#DuplicateOsgiConfiguration

WARNING 15 min fix Code smell

Conflicting or duplicate OSGi configuration targeting the same PID in the same runmode context.

Why it matters

Two files configuring the same PID in the same runmode context are both installed and the winner depends on install order. Values then differ between a fresh install and an incremental one — the classic "works on my instance" configuration bug.

How to fix it

Keep exactly one file per PID and runmode context and merge the properties into it. Split by runmode (config, config.author, config.publish) when the values genuinely differ.

text · before
ui.config/.../config/com.acme.SearchService.cfg.json         (limit = 100)
ui.config/.../config/com.acme.core.SearchService.cfg.json    (limit = 250)
text · after
ui.config/.../config/com.acme.core.services.SearchService.cfg.json   (limit = 250)

AEM-DUP-003#DuplicateSlingModel

WARNING 15 min fix Code smell

Multiple Sling Models bind to the exact same resourceType and adapter interface without condition.

Why it matters

Two Sling Models bound to the same resourceType and adaptable means HTL can resolve either one; the winner is undefined. Exported JSON then differs depending on which model the model factory picked.

How to fix it

Keep one model per resource type, or separate them by selector, resource type or a condition, and let HTL choose explicitly.

java · before
@Model(adaptables = Resource.class, resourceType = "acme/components/card")
public class CardModel { }

@Model(adaptables = Resource.class, resourceType = "acme/components/card")
public class CardViewModel { }
java · after
@Model(adaptables = Resource.class, resourceType = "acme/components/card",
       defaultInjectionStrategy = DefaultInjectionStrategy.OPTIONAL)
public class CardModel { }

@Model(adaptables = Resource.class, resourceType = "acme/components/card/view")
public class CardViewModel { }

AEM-DUP-010#DuplicateCodeBlock

WARNING 30 min fix Code smell

Duplicate Java code block or method clone detected across repository classes.

Why it matters

Cloned code drifts: a fix applied to one copy silently misses the others, and every copy has to be re-tested. Duplication across bundles is usually a missing shared module.

AEM-QUAL-001#PathBoundServletRegistration

WARNING 15 min fix Cloud Manager CQBP-75 Code smell

Sling servlet registered using paths instead of resource types (CQBP-75).

Why it matters

Cloud Manager's CQBP-75 rejects path-bound servlets because they bypass Sling's resource-centric security model and cannot be dispatched or cached like a resource. They also break the dispatcher rules teams rely on for /content URLs.

How to fix it

Register the servlet by resourceType and address it through a resource, with selectors and extensions for the variants. For a redirect or a download that genuinely has no resource, use a Sling mapping and a filter instead of /bin paths.

java · before
@SlingServlet(paths = "/bin/acme/products", methods = "GET")
public class ProductsServlet extends SlingAllMethodsServlet { }
java · after
@Component(service = Servlet.class, property = {
        ServletResolverConstants.SLING_SERVLET_RESOURCE_TYPES + "=acme/components/products",
        ServletResolverConstants.SLING_SERVLET_SELECTORS + "=list",
        ServletResolverConstants.SLING_SERVLET_EXTENSIONS + "=json"
})
public class ProductsServlet extends SlingAllMethodsServlet { }

AEM-QUAL-002#ProviderTypeImplementation

ERROR 30 min fix Cloud Manager CQBP-84 Bug

Custom code implements or extends @ProviderType product interface (CQBP-84).

Why it matters

Implementing or extending a @ProviderType interface ties your bundle to product internals that AEM as a Cloud Service upgrades without notice; CQBP-84 fails the build for exactly this reason. Provider types are contracts you consume, not implement.

How to fix it

Depend on the interface and delegate to it instead of implementing it. When you need to decorate behaviour, wrap the product object or move the logic into your own service that takes the provider type as a dependency.

java · before
public class CachedPage implements com.day.cq.wcm.api.Page {
    // re-implements a provider type: breaks on upgrade
}
java · after
@Component(service = PageTitleService.class)
public class PageTitleService {

    @Reference
    private ResourceResolverFactory resolverFactory;

    public String titleFor(String path) throws LoginException {
        Map<String, Object> auth =
                Map.of(ResourceResolverFactory.SUBSERVICE, "title-read");
        try (ResourceResolver resolver =
                     resolverFactory.getServiceResourceResolver(auth)) {
            PageManager pageManager = resolver.adaptTo(PageManager.class);
            Page page = pageManager == null ? null : pageManager.getPage(path);
            return page == null ? "" : page.getTitle();
        }
    }
}

AEM-QUAL-003#SlingSchedulerUsage

WARNING 20 min fix Cloud Manager AMSCORE-554 Security hotspot

Sling whiteboard scheduler used instead of Sling Scheduled Jobs (AMSCORE-554).

Why it matters

AMSCORE-554 flags the Sling whiteboard scheduler. AEM as a Cloud Service expects Sling Scheduled Jobs, which are cluster-aware: a job runs once across the publish tier instead of once per instance, and it survives a restart.

How to fix it

Implement a JobConsumer for the topic and schedule the run through the Sling Job API instead of Scheduler.addJob.

java · before
scheduler.add(new ImportJob(), options);
java · after
@Component(service = JobConsumer.class, immediate = true,
           property = JobConsumer.PROPERTY_TOPICS + "=acme/import")
public class ImportJobConsumer implements JobConsumer {

    @Override
    public JobResult process(Job job) {
        return JobResult.OK;
    }
}

AEM-QUAL-004#UnsafeComponentState

ERROR 20 min fix Cloud Manager AEM-3 Bug

Non-thread-safe or session-bound object stored in OSGi component field (AEM-3).

Why it matters

SlingHttpServletRequest, ResourceResolver and JCR Session are bound to one thread and one request. Stored in a component field, they leak across requests: closed resolvers are reused, sessions go stale after a restart, and the component is no longer thread-safe (Cloud Manager check AEM-3).

How to fix it

Keep only immutable, thread-safe collaborators in fields. Obtain request-scoped objects as parameters or from the request, and close them where they were created.

java · before
@Component(service = NavigationService.class)
public class NavigationService {

    private ResourceResolver resolver;   // one request's resolver, shared by all

    @Activate
    void activate(ResourceResolverFactory factory) { }
}
java · after
@Component(service = NavigationService.class)
public class NavigationService {

    @Reference
    private ResourceResolverFactory resolverFactory;

    public List<String> paths(Resource resource) {
        // the caller owns the request-scoped resolver
        return collect(resource);
    }
}

AEM-QUAL-005#AdministrativeAccessUsage

ERROR 25 min fix CWE-798 Vulnerability

Deprecated administrative login or resource resolver API used; rejected on AEM as a Cloud Service.

Why it matters

Administrative logins and loginAdministrative bypass every permission check and are rejected by AEM as a Cloud Service. They also hide the real ACLs a feature needs.

How to fix it

Create a dedicated service user with a ServiceUserMapper mapping and request a service resource resolver for that subservice, then grant the service user exactly the permissions the feature needs.

java · before

java · after
Map<String, Object> authInfo =
        Collections.singletonMap(ResourceResolverFactory.SUBSERVICE, "search");
try (ResourceResolver resolver =
             resolverFactory.getServiceResourceResolver(authInfo)) {
    // runs as the mapped service user, with its own ACLs
}

AEM-QUAL-006#ResolverStoredInComponentField

WARNING 15 min fix retired id Code smell

OSGi component stores a request-scoped ResourceResolver or JCR Session in an instance field.

Why it matters

Storing a request-scoped resolver or session in an OSGi component field keeps one request's state alive for every later request, which leaks resolvers and can serve stale content.

How to fix it

Obtain the resolver or session per request and close it in the same scope. The thread-safety owner for this check is AEM-QUAL-004 (ERROR); this id is retained so existing baselines and SARIF consumers keep working.

AEM-QUAL-008#UnprovidedMandatoryReference

ERROR 20 min fix Bug

Mandatory @Reference target is declared by project sources but registered by no component.

Why it matters

A Declarative Services component with an unsatisfied mandatory reference never activates. The bundle stays Active and the code compiles because the target type is on the classpath, so the failure is invisible until the servlet 404s or the scheduled job never fires.

How to fix it

Register an implementation with @Component(service = Target.class), or declare the reference cardinality = ReferenceCardinality.OPTIONAL when activation must not depend on it. Confirm in the Felix console that the component is satisfied.

    // ResourceResolverProvider is declared in this project...
    @Reference private ResourceResolverProvider resolverProvider;
}
// ...but no @Component implements or registers it
java · after
@Component(service = ResourceResolverProvider.class)
public class ResourceResolverProviderImpl implements ResourceResolverProvider {
    public ResourceResolver obtainResourceResolver() { ... }
}

Performance

4 issues

Resource lifecycles and repository query cost.

AEM-PERF-001#UnclosedResourceResolver

ERROR 30 min fix Bug

ResourceResolver obtained via factory is not closed in try-with-resources or finally.

Why it matters

A resolver obtained from the factory and never closed keeps its JCR session and its caches alive for the life of the JVM. AEM as a Cloud Service logs leaked resolvers and eventually refuses new ones, so the instance degrades instead of failing fast.

How to fix it

Always obtain the resolver in a try-with-resources block, or close it in a finally block, and never hand it to another thread.

java · before
ResourceResolver resolver = resolverFactory.getServiceResourceResolver(authInfo);
Resource resource = resolver.getResource(path);
return resource.adaptTo(ValueMap.class);
java · after
try (ResourceResolver resolver = resolverFactory.getServiceResourceResolver(authInfo)) {
    Resource resource = resolver.getResource(path);
    return resource == null ? Map.of() : resource.adaptTo(ValueMap.class);
}

AEM-PERF-002#UnclosedJcrSession

ERROR 30 min fix Bug

JCR Session obtained via repository login or adaptation is not logged out or closed.

Why it matters

A JCR Session opened through repository.login() or adapted from a resolver must be logged out. An open session pins the observation queue and any pending changes, and on AEM as a Cloud Service leaked sessions show up as repository connection pressure.

How to fix it

Close the session in a finally block, or avoid the session entirely: the resource resolver API covers almost every read and write a component needs.

java · before
Session session = resolver.adaptTo(Session.class);
Node node = session.getNode(path);
java · after
try (ResourceResolver resolver = resolverFactory.getServiceResourceResolver(authInfo)) {
    Resource resource = resolver.getResource(path);
    if (resource != null) {
        ValueMap properties = resource.adaptTo(ValueMap.class);
    }
}

AEM-PERF-003#OakQueryTraversalRisk

WARNING 25 min fix CWE-400 Code smell

JCR-SQL2 or XPath query lacks path or nodetype restriction, causing Oak traversal errors.

Why it matters

A JCR-SQL2 or XPath query with no path or node type restriction forces Oak to walk every index it has. At scale that is the difference between a millisecond lookup and a traversal warning in the Cloud Service logs.

How to fix it

Add a path= or type= constraint (or ISDESCENDANTNODE) so Oak can use a property index, and confirm the index exists.

sql2 · before
SELECT * FROM [nt:base] AS s
WHERE [sling:resourceType] = 'acme/components/card'
sql2 · after
SELECT * FROM [nt:base] AS s
WHERE ISDESCENDANTNODE(s, '/content/acme') AND [sling:resourceType] = 'acme/components/card'

AEM-PERF-004#UnboundedQuery

WARNING 20 min fix Code smell

JCR/Oak query has no limit and may scan an unbounded result set.

Why it matters

An unbounded query result can be enormous on a content repository that grows daily. It is the usual cause of a slow component that only shows up in production.

How to fix it

Bound the result set with p.limit (or LIMIT in JCR-SQL2) and paginate with p.offset. Report the total separately with p.guessTotal rather than materialising every hit.

java · before
Map<String, String> params = Map.of(
        "path", "/content/acme",
        "type", "cq:Page",
        "property", "jcr:content/sling:resourceType");
java · after
Map<String, String> params = new HashMap<>();
params.put("path", "/content/acme");
params.put("type", "cq:Page");
params.put("p.limit", "50");
params.put("p.offset", String.valueOf(page * 50));
params.put("p.guessTotal", "1000");

Patterns that break on AEM as a Cloud Service, including plaintext secrets.

AEM-CLOUD-001#HardcodedCloudSecret

ERROR 15 min fix CWE-798 Vulnerability

Plaintext secret or password found in OSGi configuration file.

Why it matters

A plaintext secret in a content package is readable by anyone with repository access, ends up in every environment's backup, and cannot be rotated without a code change. AEM as a Cloud Service refuses to start a service with a secret that was not supplied through a secret variable.

How to fix it

Replace the value with a secret placeholder and define the variable in Cloud Manager (or in the local .env for the SDK). Never commit the real value.

json · before
{
  "apiKey": "sk_live_9f3ac1e8b0"
}
json · after
{
  "apiKey": "$[secret:acme.apiKey]"
}

AEM-CLOUD-003#UnmappedSubserviceUser

ERROR 25 min fix Code smell

Why it matters

AEM-CLOUD-004#DeprecatedAemApiUsage

WARNING 20 min fix Cloud Manager AMSCORE-553 Code smell

Java source imports or uses an API deprecated in AEM as a Cloud Service (AMSCORE-553).

Why it matters

An API deprecated for AEM as a Cloud Service is removed or unmaintained in the product version the environment runs. The code compiles today and fails on the next upgrade.

How to fix it

Replace the call with its supported equivalent (for example the Sling ResourceResolverFactory instead of the deprecated CQ resolver helpers, and com.adobe.granite APIs instead of Classic UI ones). Check the AEM as a Cloud Service API reference for the replacement.

Security

2 issues

Output escaping and request-driven redirects.

AEM-SEC-001#UnsafeHtlContextBypass

ERROR 20 min fix CWE-79 Vulnerability

HTL expression uses @ context='unsafe' bypassing XSS protection.

Why it matters

context='unsafe' switches off HTL's contextual escaping, and the expression is written into the page verbatim. With any author-controlled or request-derived value that is a stored XSS hole (CWE-79) on a publish tier.

How to fix it

Drop unsafe and let HTL pick the context from the surrounding markup. When you really must emit markup, use context='html' and pass it through a sanitiser such as the Granite XSS API.

html · before
<div class="footer">${model.footerHtml @ context='unsafe'}</div>
html · after
<div class="footer">${model.footerHtml @ context='html'}</div>

AEM-SEC-002#OpenRedirectOrSsrf

WARNING 25 min fix CWE-601, CWE-918 Code smell

User-controlled input flows into a redirect or outbound HTTP request.

Why it matters

A request parameter that reaches sendRedirect or an outbound HTTP call lets an attacker choose the destination: an open redirect for phishing, or server-side request forgery against internal services (CWE-601).

How to fix it

Validate the destination against an allowlist of hosts or a fixed set of relative paths before redirecting, and never build an outbound URL from unvalidated input.

java · before
String target = request.getParameter("next");
response.sendRedirect(target);
java · after
String target = request.getParameter("next");
if (target != null && target.startsWith("/content/") && !target.startsWith("//")) {
    response.sendRedirect(response.encodeRedirectURL(target));
} else {
    response.sendRedirect("/content/acme/en.html");
}

AEM-COMP-002#MissingResourceTypeComponent

ERROR 15 min fix Bug

Literal sling:resourceType or data-sly-resource type names no component under the project's /apps prefix.

Why it matters

<sly data-sly-resource="${ @ resourceType='acme/components/elasticsearch/metatagrenderer'}"/>
