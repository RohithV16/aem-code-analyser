Getting started

Ten minutes from download to a dashboard your team can read. A first report needs no flags, no configuration file and no project-root argument — tuning (step 6) is optional.

Three words used throughout: a rule is the check (AEM-DEAD-001), a finding is one occurrence of it in your code, and the dashboard is the aem-analyser-report.html file a run writes.

Before you start

RequirementWhyCheck
Java 21 The analyser runs on 21. The project it reads is parsed as source, so the project’s own target does not have to be 21. java -version
Maven 3.9+ Only for the plugin route. The jar and the script need no Maven at all. mvn -v
Git Only for --changed-only, --since and the from-source route. git --version

No AEM instance, no network, no credentials. Everything is read from the file system. The analyser never connects to a repository, an author instance or a licence server, so it is safe to run in an air-gapped build agent.

1 · Run your first scan

  1. Download the CLI jar

    bash
    HOST=https://github.com/RohithV16/aem-code-analyser
cd ~/my-aem-project
curl -LO "$HOST/releases/latest/download/aem-analyser-cli.jar"

    One self-contained jar. It can live anywhere — put it in the project, in ~/tools, wherever you keep it.

    Prefer an aem-analyser command? The installer checks the jar against the release's SHA256SUMS.txt first, then writes a launcher to ~/.local/bin:

    bash
    curl -fsSLO https://raw.githubusercontent.com/RohithV16/aem-code-analyser/main/install.sh
sh install.sh
aem-analyser --version

    Pin a release with --version 1.0.10, install elsewhere with --prefix /usr/local. Below, every java -jar aem-analyser-cli.jar is the same run as aem-analyser.

  2. Run it from inside the project

    bash
    java -jar aem-analyser-cli.jar

    Where you run it decides how much is scanned: the reactor root scans the whole reactor, a module directory walks up to the reactor that owns it, and any subdirectory resolves to the nearest pom.xml above. No --project-root needed.

  3. Confirm it worked

    The console ends with a total, an execution time and a verdict. Anything other than Total Violations: 0 on a first run is normal — a mature project usually has findings:

    console output (tail)
    --------------------------------------------------------------------------------
 Total Violations: 10 (4 Errors, 5 Warnings, 1 Infos)
 Execution Time: 0.526 s
================================================================================
GATE FAILED: 4 error-severity findings detected.
================================================================================

    A run with no findings ends with GATE PASSED. The verdict reflects the default gate: any ERROR-severity finding fails it.

2 · Read the results

A CLI run prints the console report and writes one file, target/aem-analyser/aem-analyser-report.html. Add --format SARIF,HTML to write the SARIF file as well:

FileUse it for
aem-analyser-report.html The dashboard: filters, per-finding permalinks, run history, duplication and coverage panels. Opens offline, no server needed.
aem-analyser.sarif Only with --format SARIF: GitHub code scanning, Azure DevOps, any SARIF viewer.
stdout The console report: severity, rule id, file:line:column, message and the remediation sentence.
bash · open the dashboard
open target/aem-analyser/aem-analyser-report.html      # macOS
xdg-open target/aem-analyser/aem-analyser-report.html  # Linux
start target\aem-analyser\aem-analyser-report.html     # Windows

A real example, generated from the three-module fixture committed in this repository: the validation reactor report. It is produced by the current build of the site, so its header shows the version that generated it; the Maven coordinates above are the latest release.

Every rule id in the dashboard links to its entry in the issue reference — what it detects, why it matters, and the fix with a code example. Filter chips narrow by severity or family; the count next to the search box always reflects the rows you can see.

3 · Add it to the build

This is how a team uses it: one entry in the root pom.xml, and every mvn verify produces the report. The plugin comes from Maven Central — no <pluginRepositories>, no token.

pom.xml · reactor root
<build>
  <plugins>
    <plugin>
      <groupId>io.github.rohithv16</groupId>
      <artifactId>aem-analyser-maven-plugin</artifactId>
      <version>1.0.10</version>
      <!-- once, at the reactor root: module-by-module scans cannot see cross-module findings -->
      <inherited>false</inherited>
      <executions>
        <execution>
          <phase>verify</phase>
          <goals><goal>report</goal></goals>
          <configuration>
            <formats>SARIF,HTML</formats>
            <outputFile>${project.build.directory}/aem-analyser</outputFile>
          </configuration>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

About <inherited>false</inherited>. The mojos are aggregators, so the analysis always runs once at the reactor root. Without the flag the plugin is still inherited into every module and each one logs a one-line skip, which makes the build log noisy. It is a hygiene setting, not a requirement.

Run it:

bash
mvn -B -ntp verify

Result: target/aem-analyser/aem-analyser.sarif and target/aem-analyser/aem-analyser-report.html. The report goal never fails the build.

4 · Gate a pull request

Switch the goal from report to check when the report should decide whether the build passes.

pom.xml · fail on errors, not warnings
<execution>
  <phase>verify</phase>
  <goals><goal>check</goal></goals>
  <configuration>
    <failOn>ERROR</failOn>
  </configuration>
</execution>

Exit codes

CodeMeaning
0 Analysis completed and nothing tripped the gate. --fail-on NONE forces this.
1 The gate failed: at least one ERROR finding (the default), anything at or above --fail-on, --fail-on-warning, or a --min-coverage / --max-duplication / --max-warnings breach.
2 The analysis could not run — not a verdict on your code. Through Maven both 1 and 2 surface as a build failure.

From the command line the same thing is:

bash
java -jar aem-analyser-cli.jar --fail-on ERROR   # fail on errors only
java -jar aem-analyser-cli.jar --fail-on NONE    # report only, always exits 0

5 · Run it in CI

The published composite action is the shortest path: it sets up the JDK, runs the check gate, turns every finding into a native annotation on the diff, appends a severity table to the job summary and uploads the SARIF when the job allows it.

.github/workflows/quality.yml
name: Quality

on:
  pull_request:

permissions:
  contents: read
  security-events: write   # optional: lets the action upload the SARIF

jobs:
  analyse:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: RohithV16/aem-code-analyser@v1
        with:
          fail-on: ERROR
          baseline: .aem-analyser-baseline.json   # optional

Every input has a default — the two lines above (checkout and uses) are a complete gate. A version tag pins the action and the plugin it invokes together; the v1 tag is cut by the first release that ships action.yml.

Without a workflow file the same gate is one Maven goal — but it has to be check. report writes the same files and always exits 0, so a pipeline built on it can never turn red:

.github/workflows/quality.yml
name: Quality

on:
  pull_request:
  push:
    branches: [main]

jobs:
  analyse:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'

      - name: Analyse and gate
        run: |
          mvn -B -ntp io.github.rohithv16:aem-analyser-maven-plugin:1.0.10:check \
            -Daem-analyser.failOn=ERROR \
            -Daem-analyser.formats=GITHUB,SARIF,HTML \
            -Daem-analyser.outputFile=target/aem-analyser

      - name: Annotate the diff
        if: always()
        run: cat target/aem-analyser/github-annotations.txt

      - name: Upload SARIF
        uses: github/codeql-action/upload-sarif@v3
        if: always()
        with:
          sarif_file: target/aem-analyser/aem-analyser.sarif

The annotations step runs with if: always() because the gate fails the job before it — that is the point of the gate.

For SonarQube, write the SONAR format instead and point sonar.externalIssuesReportPaths at it:

bash
java -jar aem-analyser-cli.jar --format SONAR --output target/sonar
sonar-scanner -Dsonar.externalIssuesReportPaths=target/sonar/sonar-aem-analyser-report.json

6 · Tune it

Three things cover most needs: mute a rule, accept today’s findings, silence one line.

Project configuration

.aem-analyser.yml · project root
rules:
  AEM-DEAD-003B:
    enabled: false
  AEM-SEC-001:
    severity: ERROR
allowlists:
  services:
    - com.example.LegacyService
  configPaths:
    - ui.config/**/config.local/**

Accept what exists today, fail only on new findings

bash
java -jar aem-analyser-cli.jar --update-baseline
java -jar aem-analyser-cli.jar --baseline .aem-analyser-baseline.json

Silence one line

java · htl
// aem-analyser-disable-next-line AEM-DEAD-001
html (HTL)
<!-- aem-analyser-disable-next-line AEM-SEC-001 -->

Every flag, format and configuration key is listed in the CLI reference.

Troubleshooting

SymptomCause and fix
UnsupportedClassVersionError The jar is built for Java 21 and an older JVM is on PATH. Point JAVA_HOME at a 21 JDK and rerun.
“No pom.xml found” or an empty report You are outside the project. cd into the reactor or pass --project-root ~/my-aem-project.
Only part of the reactor is analysed The run was limited to one module: either you ran the CLI inside a module that is not part of the reactor, or Maven was called with -pl. Run from the reactor root, or pass --project-root.
No coverage panel in the dashboard No JaCoCo data was found. Run mvn test first, or add --collect-coverage.
Findings you expect are missing Check for a baseline (.aem-analyser-baseline.json), a muted rule in .aem-analyser.yml, or an inline suppression comment. --baseline-report keeps suppressed findings visible at INFO.
Exit code 2 The analysis failed rather than found problems. Rerun with --verbose; diagnostics for skipped files also appear in the dashboard’s Run Health tab.
