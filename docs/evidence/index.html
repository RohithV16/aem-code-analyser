Rule evidence

A linter is adopted on its quiet side. Every rule therefore ships a positive probe — a deliberate defect that must produce exactly one finding — and a clean twin that differs only by the fix and must produce none.

Download

rule-evidence.json is generated from validation/probes/evidence.json and the rule lifecycle metadata. The same bytes are packaged in the analyser jar and emitted by aem-analyser --list-rules --format json.

bash
# Rules without a clean twin: only the retired AEM-QUAL-006 should answer
aem-analyser --list-rules --format json \
  | jq '[.[] | select(.negativeProbe == null)] | length'

What a row means

FieldMeaning
positiveProbeReactor-relative file in validation/probes that contains the deliberate defect.
positiveLine / positiveSubtypeExact line and, when several sub-findings share it, the subtype that must produce one finding.
negativeProbeThe same scenario in validation/probes-clean, fixed, which must produce zero findings for this rule.
docAnchorAnchor on the generated issue reference, e.g. aem-dead-004.
status / since / replacedByThe lifecycle fields from the compatibility contract.

How CI enforces it

scripts/run-rule-probes.sh analyses both trees and runs scripts/check_rule_probes.py. It prints one PAIR OK line per rule and exits non-zero if a positive probe fires zero times or twice, or if a clean twin fires once. Reintroducing a defect into a clean twin therefore fails the run and names the rule.
