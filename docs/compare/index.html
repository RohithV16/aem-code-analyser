Compared with the Cloud Manager gate, SonarQube and Adobe’s Analyzer

“Why not just SonarQube plus the Cloud Manager gate?” is the fair question. Short answer: those two see one module at a time, and neither knows what an OSGi PID or a Sling resource type is. This page is the honest table — including where each of them is the better tool.

One sentence. AEM Code Analyser adds the whole-reactor, AEM-specific checks that per-module analysers cannot see, and it runs on a laptop with no AEM instance, no credentials and no server. It does not replace SonarQube’s dataflow analysis or the Cloud Manager gate itself.

What each tool sees

What this does not do

  • It is not a SonarQube replacement. No interprocedural taint tracking, no thirty-language coverage, no quality-gate server. If you already run SonarJava, this adds the AEM-specific, cross-module rules it cannot express.
  • It does not run anything. No AEM instance is started, no HTL is rendered and no request is issued — so it cannot measure runtime behaviour or page performance.
  • It does not host your results. Reports are files in --output; run history is a local directory. There is no dashboard service and no upload.
  • It does not decide your gate for you. The default fails on any ERROR; the threshold, the baseline and the severities are yours to set. It also does not auto-fix everything — only the fixes it can prove safe.

If you want the short version

Keep SonarQube for language-wide quality and security depth. Keep the Cloud Manager gate as the final verdict. Add AEM Code Analyser one step earlier, where it is cheapest to fix: on the developer’s machine, over the whole reactor, with the AEM semantics neither of the other two models.
