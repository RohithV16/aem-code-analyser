Compatibility contract

A gate is only useful if a green build stays green. Rule ids, their meaning and the files that remember a decision — the configuration, inline directives and the baseline — therefore change on a stated schedule, never as a side effect of a refactor.

Rule ids never silently change meaning

Every finding carries a stable id such as AEM-QUAL-004. The id is part of the public contract: it appears in SARIF, in baseline entries and in the suppression comments a team commits. Renaming an id is a major change. Fixing a false negative, adding a subtype or changing a message is a patch change, because none of those alter which id a baseline or directive names.

A rule that is superseded is first marked deprecated for one minor release (both ids resolve, new reports use the canonical id), then retired for one minor release (the old id resolves to its replacement and produces a warning), and only then may its enum constant be deleted. That is what "two-release event" means.

Status, since and replacedBy

--list-rules --format json, rule-evidence.json and the SARIF rule descriptor all carry the same three fields:

FieldValuesMeaning
statusactive, deprecated, retiredWhether the rule produces findings and whether a new configuration should use it.
sincerelease, e.g. 1.0.0First analyser release that declared the id.
replacedByrule id or nullThe rule that took over. A retired id always names one.

A configuration, inline directive or baseline that names a non-active id still resolves: enablement applies to the replacement, a suppression still hides the replacement's finding, and a baseline entry still accepts it. The CLI prints exactly one warning naming the replacement so the stale spelling is visible without failing the build. A severity written for a retired id is ignored — re-ranking the live rule from a dead id would be a silent gate change.

bash
# What the contract looks like from the outside
aem-analyser --list-rules --format json | jq -r '.[] | select(.id=="AEM-QUAL-006") | .status'
# retired

# A configuration that still says AEM-QUAL-006 warns once, then keeps working
# [WARNING] Configuration .aem-analyser.yml: AEM-QUAL-006 is retired; findings now come from AEM-QUAL-004

rule-ids.lock

rule-ids.lock at the repository root lists every id with its status, first release and replacement. It is generated from the RuleId enum and compared by a test, so deleting or re-status-ing an id without updating the lock fails the build with the id named. The lock is a review artefact, not a second source of truth: change the enum, then run scripts/check-rule-ids.sh and commit the resulting diff.

rule-ids.lock
AEM-QUAL-004|active|1.0.0|
AEM-QUAL-006|retired|1.0.0|AEM-QUAL-004

Baselines and report schemas

The baseline file carries its own schemaVersion. A change to the fingerprint algorithm bumps it, and an older file is rejected with instructions to regenerate — it is never silently mis-matched. The current version is 2; version 2 hashes the rule id, subtype, normalised path and the finding's verbatim message, so one accepted entry cannot hide a later, unrelated finding.

Minor releases may add fields to JSON, SARIF and the baseline. They do not remove or rename an existing field, change a severity's meaning, or change the id a finding carries. Removing a field or renaming a rule id is a major release with a migration note in the changelog.

ReleaseMay changeMust not change

majorId removal or rename, field removal, fingerprint/schema change.Nothing: every removal ships with a migration note and a deprecated/retired period.
